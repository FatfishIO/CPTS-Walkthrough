# Password Attacks

This module will focus on attacking and bypassing the tenet of `Authentication` by compromising user passwords in many different operating systems, applications, and encryption types.
 
Authentication, at its core, is the validation of your identity by presenting a combination of three main factors to a validation mechanism. They are;

1. Something you know (a password, passcode, pin, etc.).
2. Something you have (an ID Card, security key, or other MFA tools).
3. Something you are (your physical self, username, email address, or other identifiers.)


# Password Cracking Techniques
## Introduction to Password Cracking

|**Category**|**Details**|
|---|---|
|**Core Concepts**||
|Password storage|Hashed; hashing transforms arbitrary input bytes into fixed-size output (MD5, SHA-256)|
|Example|`echo -n Soccer06! \| md5sum` → `40291c1d19ee11a7df8495c4cccefdfa`; `echo -n Soccer06! \| sha256sum` → `a025dc6fabb09c2b8bfe23b5944635f9b68433ebd9a1a09453dd4fee00766d93`|
|One-way function|Should not be possible to figure out original password from hash alone|
|Password cracking|Attempting to reverse hash; common techniques: rainbow tables, dictionary attacks, brute-force attacks (last resort)|
|**Rainbow Tables**||
|Definition|Large pre-compiled maps of input and output values for a given hash function; can quickly identify password if hash already mapped|
|Examples|`123456` → `e10adc3949ba59abbe56e057f20f883e`; `password` → `5f4dcc3b5aa765d61d8327deb882cf99`; `rockyou` → `f806fc5a2a0d5ba2471600758452799c`; `abc123` → `e99a18c428cb38d5f260853678922e03`|
|**Salting**||
|Definition|Random sequence of bytes added to password before hashing; should not be reused|
|Effect|Same password + salt → different hash (e.g., `Th1sIsTh3S@lt_Soccer06!` → `90a10ba83c04e7996bc53373170b5474`)|
|Not secret|System needs salt to check authentication; salts typically prepended to hashes|
|Effectiveness|Even if password mapped, salt+password combination likely not; one-byte salt = 15 billion entries → 3.84 trillion (factor of 256)|
|**Brute-force Attack**||
|Definition|Attempting every possible combination of letters, numbers, symbols until correct password discovered|
|Time|Can take very long; shorter passwords (<9 characters) viable even on consumer hardware|
|Effectiveness|Only technique 100% effective (given enough time, any password cracked)|
|Practicality|Hardly used due to time; replaced by more efficient mask attacks|
|Examples|`Sxejd` → `2cdc813ef26e6d20c854adb107279338`; `Sxeje` → `7703349a1f943f9da6d1dfcda51f3b63`; etc.|
|Speed|Depends on hashing algorithm and hardware; hashcat ~5 million passwords/second attacking MD5 vs. ~10,000/second targeting DCC2 hash on typical company laptop|
|**Dictionary Attack**||
|Definition|Wordlist attack; most efficient for cracking passwords, especially under time constraints|
|Approach|List containing statistically likely passwords rather than every character combination|
|Wordlists|`rockyou.txt`, SecLists|
|`head --lines=20 /usr/share/wordlists/rockyou.txt`|`123456`, `12345`, `123456789`, `password`, `iloveyou`, `princess`, `1234567`, `rockyou`, `12345678`, `abc123`, `nicole`, `daniel`, `babygirl`, `monkey`, `lovely`, `jessica`, `654321`, `michael`, `ashley`, `qwerty`|
|Note|rockyou.txt = over 14 million real passwords leaked when RockYou website hacked in 2009; company stored all user passwords unencrypted|

## Introduction to John The Ripper

|**Category**|**Details**|
|---|---|
|**Core Concepts**||
|John the Ripper (JtR)|Well-known pentesting tool for cracking passwords via brute-force and dictionary attacks; open-source; first released 1996; initially for UNIX|
|Jumbo variant|Recommended: performance optimizations, additional features (multilingual word lists), 64-bit support; greater accuracy and speed|
|Included tools|Various tools for converting different file types/hashes into JtR-usable formats|
|Updates|Regularly updated to keep up with security trends|
|**Cracking Modes — Single Crack**||
|Definition|Rule-based cracking technique; most useful targeting Linux credentials|
|Generates candidates|Based on victim's username, home directory name, GECOS values (full name, room number, phone number, etc.)|
|Rules|Large set of rules applying common string modifications (e.g., Bob Smith → Smith1)|
|Example|`r0lf:$6$ues25dIanlctrWxg$nZHVz2z4kCy1760Ee28M1xtHdGoy0C2cYzZ8l2sVa1kIa8K9gAcdBP.GI6ng/qA4oaMrgElZ1Cb9OeXO4Fvy3/:0:0:Rolf Sebastian:/home/r0lf:/bin/bash`|
|Command|`john --single passwd`|
|Output|Loaded 1 password hash (sha512crypt, crypt(3) $6$ [SHA512 256/256 AVX2 4x]); Cost 1 (iteration count) is 5000; Will run 4 OpenMP threads; cracked password|
|**Cracking Modes — Wordlist**||
|Definition|Dictionary attack; attempts all passwords in supplied wordlist against password hash|
|Syntax|`john --wordlist=<wordlist_file> <hash_file>`|
|Wordlist format|Plain text; one word per line; multiple wordlists separated by commas|
|Rules|`--rules` argument; custom or built-in; transformations (appending numbers, capitalizing letters, adding special characters)|
|**Cracking Modes — Incremental**||
|Definition|Powerful, brute-force-style; generates candidates based on statistical model (Markov chains); prioritizes more likely passwords based on training data|
|Characteristics|Most exhaustive but most time-consuming; generates dynamically; no predefined wordlist|
|Efficiency|Significantly more efficient than naïve brute-force|
|Syntax|`john --incremental <hash_file>`|
|Default modes|Predefined in `john.conf` (character sets and password lengths)|
|`grep '# Incremental modes' -A 100 /etc/john/john.conf`|`[Incremental:Custom]` (custom.chr, MinLen=0), `[Incremental:UTF8]` (utf8.chr, CharCount=196), `[Incremental:Latin1]` (latin1.chr, CharCount=203), `[Incremental:ASCII]` (ascii.chr, MaxLen=13, CharCount=95)|
|Note|Resource-intensive and slow for long/complex passwords; customize character set and length|
|**Identifying Hash Formats**||
|Problem|Hashes may appear in unknown format; JtR may not identify with complete certainty|
|Resources|JtR's sample hash documentation; PentestMonkey list; hashID tool|
|`hashid -j 193069ceb0461e1d40d216e32c79c704`|Analyzes hash; suggests formats with JtR format (`-j` flag): MD2 (md2), MD5 (raw-md5), MD4 (raw-md4), Double MD5, LM (lm), RIPEMD-128 (ripemd-128), Haval-128 (haval-128-4), Tiger-128, Skein-256(128), Skein-512(128), Lotus Notes/Domino 5 (lotus5), Skype, Snefru-128 (snefru-128), NTLM (nt), Domain Cached Credentials (mscach), Domain Cached Credentials 2 (mscach2), DNSSEC(NSEC3), RAdmin v2.x (radmin)|

|`--format` argument|Instruct JtR which format target hashes have|

## Introduction to Hashcat

|**Category**|**Details**|
|---|---|
|**Core Concepts**||

## Writing Custom Wordlists and Rules

|**Category**|**Details**|
|---|---|
|**Core Concepts**||
|Human tendency|Users create weak passwords despite policies; follow predictable patterns (service name, company name, pets, friends, sports, hobbies)|
|Common additions|First letter uppercase (Password), adding numbers (Password123), adding year (Password2022), adding month (Password02), exclamation mark (Password2022!), special characters (P@ssw0rd2022!)|
|Statistics|Most passwords no longer than ten characters (WP Engine)|
|Approach|Select familiar terms ≥5 characters (pet names, hobbies, preferences); append year + special character; modify by changing month or incrementing digit|
|**Hashcat Rule Syntax**||
|`:`|Do nothing|
|`l`|Lowercase all letters|
|`u`|Uppercase all letters|
|`c`|Capitalize first letter and lowercase others|
|`sXY`|Replace all instances of X with Y|
|`$!`|Add exclamation character at end|
|Each rule|Written on new line; determines how word should be transformed|
|**Example — custom.rule**||
|Content|`:`, `c`, `so0`, `c so0`, `sa@`, `c sa@`, `c sa@ so0`, `$!`, `$! c`, `$! so0`, `$! sa@`, `$! c so0`, `$! c sa@`, `$! so0 sa@`, `$! c so0 sa@`|

|**Category**|**Details**|

# Extracting Passwords from Linux Systems
## Linux Authentication Process

|**Category**|**Details**|
|---|---|
|**Core Concepts**||
|PAM|Pluggable Authentication Modules — commonly used authentication mechanism; modules manage user info, authentication, sessions, password changes|
|Module location|`/usr/lib/x86_64-linux-gnu/security/` on Debian-based systems (e.g., `pam_unix.so`, `pam_unix2.so`)|
|Example|`passwd` command invokes PAM; `pam_unix.so` uses standardized API calls to update account info; reads/writes `/etc/passwd` and `/etc/shadow`|
|Other PAM modules|LDAP, mount operations, Kerberos authentication|
|**Passwd File**||
|Location|`/etc/passwd`; readable by all users and services|
|Format|Seven fields separated by colons (`:`)|
|Example|`htb-student:x:1000:1000:,,,:/home/htb-student:/bin/bash`|
|Fields|Username (`htb-student`), Password (`x`), User ID (`1000`), Group ID (`1000`), GECOS (`,,,`), Home directory (`/home/htb-student`), Default shell (`/bin/bash`)|
|Password field|Rarely holds actual hash (very old systems); modern systems store hashes in `/etc/shadow`; `x` indicates hashed form in shadow|
|Risk|World-readable → attackers can crack passwords if hashes stored here; if writeable → remove password field for root user (`root::0:0:root:/root:/bin/bash`) → no password prompt for `su`|
|**Shadow File**||
|Location|`/etc/shadow`; solely responsible for password storage/management; only readable by administrative privileges|
|Format|Nine fields separated by colons (`:`)|
|Example|`htb-student:$y$j9T$3QSBB6CbHEu...SNIP...f8Ms:18955:0:99999:7:::`|
|Fields|Username (`htb-student`), Password (`$y$j9T$...`), Last change (`18955`), Min age (`0`), Max age (`99999`), Warning period (`7`), Inactivity period (`-`), Expiration date (`-`), Reserved field (`-`)|
|Password field special chars|`!` or `*` → user cannot log in using Unix password (other auth methods still possible); empty → no password required|
|Password format|`$<id>$<salt>$<hashed>`|
|**Hash Algorithm IDs**||
|`1`|MD5|
|`2a`|Blowfish|
|`5`|SHA-256|
|`6`|SHA-512|
|`sha1`|SHA1crypt|
|`y`|Yescrypt (default on many Linux distributions including Debian)|
|`gy`|Gost-yescrypt|
|`7`|Scrypt|
|**Opasswd**||
|Location|`/etc/security/opasswd`; previous passwords stored by `pam_unix.so`; requires root privileges to read|
|Example|`cry0l1t3:1000:2:$1$HjFAfYTG$qNDkF0zJ3v8ylCOrKB0kt0,$1$kcUjWZJX$E9uMSmiQeRh4pAAgzuvkq1`|
|Note|MD5 (`$1$`) easier to crack than SHA-512; users often reuse similar passwords across services|
|**Cracking Linux Credentials**||
|Tool|`unshadow` (included with John the Ripper) — combines passwd and shadow files into single file suitable for cracking|
|`sudo cp /etc/passwd /tmp/passwd.bak`|Copy passwd file|
|`sudo cp /etc/shadow /tmp/shadow.bak`|Copy shadow file|
|`unshadow /tmp/passwd.bak /tmp/shadow.bak > /tmp/unshadowed.hashes`|Combine files|
|`hashcat -m 1800 -a 0 /tmp/unshadowed.hashes rockyou.txt -o /tmp/unshadowed.cracked`|Crack with hashcat (mode 1800 for sha512crypt)|
|Note|Exact scenario JtR's single crack mode was designed for|

# Password Management
## Password Policies

|**Category**|**Details**|
|---|---|
|**Core Concepts**||
|Password policy|Set of rules designed to enhance computer security by encouraging users to create strong passwords and use them appropriately according to organization's standards|
|Scope|Extends beyond minimum password requirements to encompass entire password lifecycle (creation, storage, management, transmission)|
|Components|Definition (rules/expectations) + Enforcement (technology to enforce compliance) — both essential|
|Example|Mark (new employee) tries `password123` → error: does not meet policy; chooses `Inlanefreight01!` → meets policy but still weak (includes company name)|
|**Password Policy Standards**||
|Purpose|Compliance requirements and best practices; defines baseline for security controls; compliance alone should not be sole measure of security|
|Common standards|NIST SP800-63B, CIS Password Policy Guide, PCI DSS|
|Differing perspectives|Password expiration — industry has shifted to recommending password expiration be disabled (leads users to adopt predictable, weak patterns)|
|**Sample Password Policy**||
|Minimum length|8 characters|
|Case|Include uppercase and lowercase letters|
|Number|Include at least one number|
|Special character|Include at least one special character|
|Username restriction|Should not be the username|
|Expiration|Changed every 60 days|
|Weakness example|`Inlanefreight01!` meets policy but weak (company name); after expiration, change `01` to `02` → still complies despite nearly identical|
|**Recommended Blacklisted Words**||
|Company-related|Company's name, common words associated with company|
|Time-related|Names of months, names of seasons|
|Common words|Variations on "welcome" and "password"|
|Easily guessable|`password`, `123456`, `abcde`|
|**Enforcing Password Policy**||
|Technical enforcement|Most applications and identity management systems offer features; Active Directory: configure Password Policy GPO|
|Communication|Policy must be communicated to rest of company|
|Processes/procedures|Created to guarantee password policy is applied everywhere|
|**Creating a Strong Password**||
|Tools|PasswordMonster (evaluate strength), 1Password Password Generator (generate secure ones)|
|Strong example|`CjDC2x[U` — rated very strong; contains lowercase, uppercase, numbers, symbols; estimated crack time: 1 thousand years|
|Memorable strong passwords|Ordinary words, phrases, song lyrics (e.g., `This is my secure password`, `The name of my dog is Popy`); add special characters (e.g., `()The name of my dog is Popy!`)|
|Estimated crack time|`The name of my dog is Popy` — very strong; 381 trillion years|
|Caution|Attackers can use OSINT to learn about us; keep this in mind when creating passwords|
|Management|As number of passwords grows, difficult to manage all; password manager can help generate and securely store large numbers|

## Password Managers

|**Category**|**Details**|
|---|---|
|**Core Concepts**||
|Context|Average person has ~100 passwords (NordPass); leads to reuse/oversimplification; need strong, unique passwords per service|
|Password manager|Application securely storing passwords and sensitive information in encrypted database; features: password generation, 2FA support, secure form filling, browser integration, multi-device synchronization, security alerts|
|**How Password Managers Work**||
|Master password|Most operate using master password to encrypt password database|
|Cryptography|Encryption and authentication rely on cryptographic hash functions and key derivation functions to prevent unauthorized access; mechanisms depend on provider and whether cloud-based or locally stored|
|**Cloud Password Managers**||
|Convenience|Synchronize encrypted password database across multiple devices (average person owns 3-4 devices); provide mobile app, browser add-on|
|Vendor documentation|Bitwarden, 1Password, LastPass whitepapers|
|Common implementation|Deriving encryption keys from master password; supports Zero-Knowledge Encryption (no one, not even provider, can access secured data)|
|Bitwarden's approach|Master key (derived from master password using KDF); Master password hash (generated using master password + master key to authenticate user to cloud service); Decryption key (created using master key to form symmetric key, used to decrypt vault items); PBKDF2-SHA256 algorithm; AES-256 bit decryption|
|Popular cloud managers|1Password, Bitwarden, Dashlane, Keeper, Lastpass, NordPass, RoboForm|
|**Local Password Managers**||
|Preference|Companies/individuals managing own security, not relying on third-party services; store password database locally; user responsible for protecting content and storage location|
|Dashlane blog post|Password Manager Storage: Cloud vs. Local — explores pros/cons; "At first it might seem like this makes local storage more secure than cloud storage, but cybersecurity is not a simple discipline"|
|Encryption|Similar to cloud-based; focus on securing database stored on local system; various cryptographic hash functions (depending on manufacturer); key derivation functions with random salt to prevent precomputed keys and hinder dictionary/guessing attacks|
|Additional protections|Memory protection, keylogger resistance, secure desktop environment similar to Windows UAC|
|Popular local managers|KeePass, KWalletManager, Pleasant Password Server, Password Safe|
|**Features**||
|Common features|2FA support, Multi-platform (Android, iOS, Windows, Linux, Mac, etc.), Browser Extension, Login Autocomplete, Import/export capabilities, Password generation|
|Selection factors|Devices used, synchronization needs, 2FA, budget|
|Resources|Wikipedia list of online and offline password managers with key capabilities|
|**Alternatives**||
|Context|Passwords most common form of authentication but not only one; can be compromised via cracking, guessing, shoulder surfing, etc.|
|Common alternatives|Multi-factor Authentication (MFA), FIDO2 (open authentication standard enabling passwordless logins using physical devices like YubiKey; Microsoft's supported FIDO2 providers), One-Time Passwords (OTP), Time-Based One-Time Passwords (TOTP), IP restrictions, Device compliance enforcement (Microsoft Endpoint Manager, Workspace ONE)|
|**Going Passwordless**||
|Advocates|Microsoft, Auth0, Okta, Ping Identity|
|Definition|Achieved when authentication factor other than password is used; password = knowledge factor (something a user knows); vulnerable to theft, sharing, repeat use, misuse; passwordless relies on possession factor (something a user has) or inherent factor (something a user is)|
|Resources|Microsoft Passwordless, Auth0 Passwordless, Okta Passwordless, PingIdentity|
|**Key Takeaway**||
|Choice|Depends on specific needs of individual or organization; common to use different password protection methods for different purposes|

# Skills Assessment - Password Attacks
**The Credential Theft Shuffle**
The Credential Theft Shuffle, as coined by Sean Metcalf, is a systematic approach attackers use to compromise Active Directory environments by exploiting stolen credentials. The process begins with gaining initial access, often through phishing, followed by obtaining local administrator privileges on a machine. Attackers then extract credentials from memory using tools like Mimikatz and leverage these credentials to move laterally across the network. Techniques such as pass-the-hash (PtH) and tools like NetExec facilitate this lateral movement and further credential harvesting. The ultimate goal is to escalate privileges and gain control over the domain, often by compromising Domain Admin accounts or performing DCSync attacks. Sean emphasizes the importance of implementing security measures such as the Local Administrator Password Solution (LAPS), enforcing multi-factor authentication, and restricting administrative privileges to mitigate such attacks.
