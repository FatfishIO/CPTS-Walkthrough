# Information Gathering - Web Edition

# Introduction

|**Command / Option**|**Description**|
|---|---|
|**Core Concepts**||
|Web Reconnaissance|Foundation of security assessment; systematic/meticulous collection of info about target website/app; part of "Information Gathering" phase|
|**Primary Goals**||
|Identifying Assets|Uncover all publicly accessible components (web pages, subdomains, IP addresses, technologies)|
|Discovering Hidden Information|Locate sensitive info inadvertently exposed (backup files, config files, internal docs)|
|Analysing the Attack Surface|Examine attack surface to identify vulnerabilities/weaknesses (technologies, configurations, entry points)|
|Gathering Intelligence|Collect info for exploitation/social engineering (key personnel, email addresses, behavior patterns)|
|Purpose|Attackers tailor attacks; defenders proactively identify and patch vulnerabilities|
|**Types of Reconnaissance**||
|Active Reconnaissance|Directly interacts with target system to gather information|
|Passive Reconnaissance|Gathers information without directly interacting with target|
|**Active Reconnaissance Techniques**||
|Port Scanning|Identify open ports/services (e.g., Nmap scan for 80/443); Risk: High|
|Vulnerability Scanning|Probe for known vulnerabilities (e.g., Nessus for SQLi/XSS); Risk: High|
|Network Mapping|Map network topology (e.g., traceroute); Risk: Medium to High|
|Banner Grabbing|Retrieve info from service banners (e.g., Netcat/curl HTTP banner); Risk: Low|
|OS Fingerprinting|Identify target OS (e.g., Nmap `-O`); Risk: Low|
|Service Enumeration|Determine specific versions of services (e.g., Nmap `-sV`); Risk: Low|
|Web Spidering|Crawl website for pages/directories/files (e.g., Burp Suite Spider, OWASP ZAP Spider, Scrapy); Risk: Low to Medium|
|**Passive Reconnaissance Techniques**||
|Search Engine Queries|Uncover info via search engines (Google, DuckDuckGo, Bing, Shodan); Risk: Very Low|
|WHOIS Lookups|Retrieve domain registration details (`whois`); Risk: Very Low|
|DNS|Analyze DNS records for subdomains/mail servers (`dig`, `nslookup`, `host`, `dnsenum`, `fierce`, `dnsrecon`); Risk: Very Low|
|Web Archive Analysis|Examine historical snapshots (Wayback Machine); Risk: Very Low|
|Social Media Analysis|Gather info from LinkedIn, Twitter, Facebook; Risk: Very Low|
|Code Repositories|Analyze public code repos (GitHub, GitLab) for exposed credentials/vulnerabilities; Risk: Very Low|
|**Key Takeaways**||
|Active vs Passive|Active = direct interaction, comprehensive but higher detection risk; Passive = stealthier but less comprehensive|
|Module focus|Tools & techniques starting with WHOIS; foundational knowledge for advanced recon|

# WHOIS
## WHOIS

|**Command / Option**|**Description**|
|---|---|
|**Core Concepts**||
|WHOIS|Query and response protocol to access databases storing info about registered internet resources (domain names, IP address blocks, autonomous systems)|
|Analogy|Giant phonebook for the internet — look up who owns/is responsible for online assets|
|**Command**||
|`whois inlanefreight.com`|Query WHOIS records for a domain|
|**WHOIS Record Contents**||
|Domain Name|The domain name itself (e.g., example.com)|
|Registrar|Company where domain was registered (e.g., GoDaddy, Namecheap)|
|Registrant Contact|Person/organization that registered the domain|
|Administrative Contact|Person responsible for managing the domain|
|Technical Contact|Person handling technical issues|
|Creation and Expiration Dates|When domain was registered / when it expires|
|Name Servers|Servers translating domain name into IP address|
|**History**||
|Origin|1970s — Elizabeth Feinler & team at Stanford Research Institute's NIC created WHOIS directory for ARPANET|
|Purpose|Rudimentary database storing network users, hostnames, domain names|
|**Why WHOIS Matters for Web Recon**||
|Identifying Key Personnel|Names, email addresses, phone numbers → social engineering / phishing targets|
|Discovering Network Infrastructure|Name servers, IP addresses → clues about network infrastructure, entry points, misconfigurations|
|Historical Data Analysis|Historical WHOIS records (e.g., WhoisFreaks) → changes in ownership/contact/technical details over time|

## Utilising WHOIS

|**Command / Option**|**Description**|
|---|---|
|**Scenarios**||
|Phishing Investigation|WHOIS on suspicious domain → recent registration, hidden registrant, bulletproof hosting NS → red flags for phishing campaign|
|Malware Analysis|WHOIS on C2 domain → free email registrant, high-cybercrime country, lax registrar → likely compromised/bulletproof server|
|Threat Intelligence Report|WHOIS on multiple domains → registration clusters, aliases/fake identities, shared name servers, takedown history → TTPs + IOCs|
|**Installation**||
|`sudo apt update`|Update package lists|
|`sudo apt install whois -y`|Install whois utility|
|**Command**||
|`whois facebook.com`|Perform WHOIS lookup|
|**Reading Output**||
|Domain Registration|Registrar, Creation Date, Expiry Date — indicates legitimacy and established presence|
|Domain Owner|Registrant/Admin/Tech Organization + Contact (e.g., Meta Platforms, Inc. / Domain Admin)|
|Domain Status|`clientDeleteProhibited`, `clientTransferProhibited`, `clientUpdateProhibited`, `serverDeleteProhibited`, `serverTransferProhibited`, `serverUpdateProhibited` — protected against unauthorized changes|
|Name Servers|e.g., `A.NS.FACEBOOK.COM`, `B.NS.FACEBOOK.COM` — large orgs manage own DNS infrastructure|
|**Key Takeaways**||
|Limitation|WHOIS may not directly identify individual employees or vulnerabilities|
|Approach|Combine WHOIS data with other reconnaissance techniques for comprehensive digital footprint|

# DNS & SUBDOMAIN
## DNS

|**Command / Option**|**Description**|
|---|---|
|**Core Concepts**||
|DNS|Domain Name System — internet's GPS; translates human-readable domain names into numerical IP addresses|
|Analogy|Like GPS translating destination names into latitude/longitude|
|Without DNS|Navigating online world would be like driving without a map|
|**How DNS Works**||
|DNS Query|Computer checks cache; if not found, reaches out to DNS resolver (usually ISP-provided)|
|Recursive Lookup|Resolver checks its cache; if not found, starts journey through DNS hierarchy|
|Root Name Server|Doesn't know exact address but knows TLD name server responsible; points resolver in right direction|
|TLD Name Server|Knows which authoritative name server is responsible for the specific domain; sends resolver there|
|Authoritative Name Server|Final stop; holds correct IP address and sends it back to resolver|
|Resolver Returns Info|Receives IP, gives it to computer, caches it|
|Computer Connects|Computer connects directly to web server hosting the website|
|**Hosts File**||
|Purpose|Simple text file mapping hostnames to IP addresses; manual method bypassing DNS|
|Windows path|`C:\Windows\System32\drivers\etc\hosts`|
|Linux/MacOS path|`/etc/hosts`|
|Format|`<IP Address> <Hostname> [<Alias> ...]`|
|Example|`127.0.0.1 localhost` / `192.168.1.10 devserver.local`|
|Edit|Open with administrative/root privileges; changes take effect immediately|
|Common uses|Redirect domain to local server for development; test connectivity; block unwanted websites (`0.0.0.0 unwanted-site.com`)|
|**Key DNS Concepts**||
|Zone|Distinct part of domain namespace managed by specific entity/administrator (virtual container)|
|Zone file|Text file on DNS server defining resource records within the zone|
|`$TTL 3600`|Default Time-To-Live (1 hour)|
|`@ IN SOA`|Start of Authority record (serial, refresh, retry, expire, minimum TTL)|
|`@ IN NS`|Authoritative name servers|
|`@ IN MX 10 mail.example.com.`|Mail server record|
|`www IN A 192.0.2.1`|A record mapping hostname to IPv4|
|`ftp IN CNAME www.example.com.`|CNAME alias record|
|**DNS Concepts Table**||
|Domain Name|Human-readable label (e.g., `www.example.com`)|
|IP Address|Unique numerical identifier (e.g., `192.0.2.1`)|
|DNS Resolver|Server translating domain names to IPs (ISP DNS or public like `8.8.8.8`)|
|Root Name Server|Top-level servers in DNS hierarchy; 13 worldwide named A-M (`a.root-servers.net`)|
|TLD Name Server|Servers for specific TLDs (Verisign for `.com`, PIR for `.org`)|
|Authoritative Name Server|Holds actual IP address for a domain (managed by hosting providers/registrars)|
|DNS Record Types|Different types of info stored in DNS (A, AAAA, CNAME, MX, NS, TXT, etc.)|
|**DNS Record Types**||
|A (Address Record)|Maps hostname to IPv4 address (`www.example.com. IN A 192.0.2.1`)|
|AAAA (IPv6 Address Record)|Maps hostname to IPv6 address (`www.example.com. IN AAAA 2001:db8:85a3::8a2e:370:7334`)|
|CNAME (Canonical Name Record)|Creates alias for hostname pointing to another hostname (`blog.example.com. IN CNAME webserver.example.net.`)|
|MX (Mail Exchange Record)|Specifies mail server(s) for domain (`example.com. IN MX 10 mail.example.com.`)|
|NS (Name Server Record)|Delegates DNS zone to specific authoritative name server (`example.com. IN NS ns1.example.com.`)|
|TXT (Text Record)|Stores arbitrary text (domain verification, security policies) (`example.com. IN TXT "v=spf1 mx -all"`)|
|SOA (Start of Authority Record)|Administrative info about zone (primary NS, responsible person email, parameters)|
|SRV (Service Record)|Defines hostname and port for specific services (`_sip._udp.example.com. IN SRV 10 5 5060 sipserver.example.com.`)|
|PTR (Pointer Record)|Reverse DNS lookups — maps IP to hostname (`1.2.0.192.in-addr.arpa. IN PTR www.example.com.`)|
|**Class Field "IN"**||
|Meaning|Stands for "Internet" — protocol family; denotes Internet protocol suite (IP)|
|Other classes|CH (Chaosnet), HS (Hesiod) — rarely used in modern DNS|
|**Why DNS Matters for Web Recon**||
|Uncovering Assets|DNS records reveal subdomains, mail servers, name servers; CNAME to outdated server → vulnerable system|
|Mapping Network Infrastructure|Analyse DNS data to map target's network; NS records reveal hosting provider; A records pinpoint load balancers|
|Monitoring for Changes|Continuous DNS monitoring reveals infrastructure changes; new subdomain (`vpn.example.com`) → new entry point; TXT record (`_1password=...`) → social engineering targets|

## Digging DNS

|**Command / Option**|**Description**|
|---|---|
|**DNS Tools**||
|`dig`|Versatile DNS lookup tool; supports various query types (A, MX, NS, TXT); detailed output; manual queries, zone transfers, troubleshooting|
|`nslookup`|Simpler DNS lookup tool; primarily A, AAAA, MX records; basic queries, quick checks|
|`host`|Streamlined DNS lookup tool with concise output; quick checks of A, AAAA, MX records|
|`dnsenum`|Automated DNS enumeration; dictionary attacks, brute-forcing, zone transfers; discovering subdomains|
|`fierce`|DNS reconnaissance and subdomain enumeration; recursive search, wildcard detection; user-friendly interface|
|`dnsrecon`|Combines multiple DNS reconnaissance techniques; supports various output formats; comprehensive enumeration|
|`theHarvester`|OSINT tool; gathers info from various sources including DNS records (email addresses)|
|Online DNS Lookup Services|User-friendly interfaces; quick lookups when CLI tools unavailable|
|**dig Commands**||
|`dig domain.com`|Default A record lookup|
|`dig domain.com A`|Retrieve IPv4 address (A record)|
|`dig domain.com AAAA`|Retrieve IPv6 address (AAAA record)|
|`dig domain.com MX`|Find mail servers (MX records)|
|`dig domain.com NS`|Identify authoritative name servers|
|`dig domain.com TXT`|Retrieve TXT records|
|`dig domain.com CNAME`|Retrieve canonical name (CNAME) record|
|`dig domain.com SOA`|Retrieve start of authority (SOA) record|
|`dig @1.1.1.1 domain.com`|Specify a specific name server to query|
|`dig +trace domain.com`|Show full path of DNS resolution|
|`dig -x 192.168.1.1`|Reverse lookup on IP address to find associated hostname|
|`dig +short domain.com`|Short, concise answer|
|`dig +noall +answer domain.com`|Display only the answer section|
|`dig domain.com ANY`|Retrieve all available DNS records (many servers ignore ANY per RFC 8482)|
|**Caution**||
|Rate limits|Some servers detect and block excessive DNS queries; respect rate limits; obtain permission before extensive recon|
|**dig Output Sections**||
|Header|`opcode: QUERY`, `status: NOERROR`, `id`; flags (`qr` = Query Response, `rd` = Recursion Desired, `ad` = Authentic Data); counts (QUERY, ANSWER, AUTHORITY, ADDITIONAL)|
|Question Section|Specifies the question (e.g., `;google.com. IN A`)|
|Answer Section|The answer (e.g., `google.com. 0 IN A 142.251.47.142`); `0` = TTL|
|Footer|Query time, SERVER (DNS server + protocol), WHEN (timestamp), MSG SIZE|
|**OPT Pseudosection**||
|EDNS|Extension Mechanisms for DNS — allows larger message sizes and DNSSEC support|
|**Example — dig +short**||
|`dig +short hackthebox.com`|Returns only IP addresses (e.g., `104.18.20.126`, `104.18.21.126`)|

## Subdomains

|**Command / Option**|**Description**|
|---|---|
|**Core Concepts**||
|Subdomains|Extensions of the main domain; organize/separate website sections (e.g., `blog.example.com`, `shop.example.com`, `mail.example.com`)|
|**Why Important for Web Recon**||
|Development/Staging Environments|Used to test features before deployment; relaxed security → vulnerabilities/sensitive info exposed|
|Hidden Login Portals|Administrative panels or login pages not meant to be public; attractive targets|
|Legacy Applications|Older forgotten apps; outdated software with known vulnerabilities|
|Sensitive Information|Confidential documents, internal data, configuration files inadvertently exposed|
|**Subdomain Enumeration**||
|Definition|Systematically identifying and listing subdomains|
|DNS representation|A (or AAAA) records map subdomain to IP; CNAME records create aliases|
|**1. Active Subdomain Enumeration**||
|Method|Directly interact with target's DNS servers|
|Zone transfer|Misconfigured server may leak complete list of subdomains; rarely successful due to tightened security|
|Brute-force enumeration|Systematically test list of potential subdomain names; tools: `dnsenum`, `ffuf`, `gobuster`; uses wordlists of common names or custom-generated patterns|
|**2. Passive Subdomain Enumeration**||
|Method|Rely on external sources without directly querying target's DNS servers|
|Certificate Transparency (CT) logs|Public repositories of SSL/TLS certificates; include subdomains in Subject Alternative Name (SAN) field|
|Search engines|Google, DuckDuckGo; use operators like `site:` to filter results|
|Online databases/tools|Aggregate DNS data from multiple sources|
|**Comparison**||
|Active|More control, comprehensive discovery, but more detectable|
|Passive|Stealthier but might not uncover all subdomains|
|Best approach|Combine both for thorough and effective enumeration|

## DNS Zone Transfers

|**Command / Option**|**Description**|
|---|---|
|**Core Concepts**||
|DNS Zone Transfer|Wholesale copy of all DNS records within a zone from one name server to another; essential for consistency and redundancy|
|Vulnerability|If not adequately secured, unauthorized parties can download entire zone file → complete subdomain list, IP addresses, sensitive DNS data|
|**Zone Transfer Process (AXFR)**||
|Zone Transfer Request (AXFR)|Secondary DNS server sends zone transfer request to primary server|
|SOA Record Transfer|Primary responds with Start of Authority (SOA) record (serial number helps secondary determine if zone data is current)|
|DNS Records Transmission|Primary transfers all DNS records (A, AAAA, MX, CNAME, NS, etc.) one by one|
|Zone Transfer Complete|Primary signals end of transfer|
|Acknowledgement (ACK)|Secondary confirms successful receipt/processing|
|**Zone Transfer Vulnerability**||
|Core issue|Access controls governing who can initiate a zone transfer|
|Historical|Early internet allowed any client to request zone transfer; simplified admin but opened security hole|
|Information revealed|Subdomains (development, staging, admin panels), IP addresses, name server records (hosting provider, misconfigurations)|
|**Remediation**||
|Modern practice|Allow zone transfers only to trusted secondary servers|
|Risk remains|Misconfigurations due to human error or outdated practices|
|Value|Attempting zone transfer (with authorization) remains valuable recon technique; can reveal DNS server configuration/security posture|
|**Exploiting Zone Transfers**||
|`dig axfr @nsztm1.digi.ninja zonetransfer.me`|Request full zone transfer (AXFR) from DNS server|
|Result|If misconfigured, returns complete list of DNS records including all subdomains|
|Example output|SOA, HINFO, TXT, MX, A, NS, SRV, PTR, AFSDB records; `XFR size: 50 records`|
|Note|`zonetransfer.me` is a service specifically set up to demonstrate zone transfer risks|

## Virtual Hosts

|**Command / Option**|**Description**|
|---|---|
|**Core Concepts**||
|Virtual Hosting|Web servers (Apache, Nginx, IIS) host multiple websites/apps on a single server; differentiate by domains/subdomains|
|Mechanism|Leverages HTTP **Host header** in every request|
|**VHosts vs Subdomains**||
|Subdomains|Extensions of main domain (e.g., `blog.example.com`); typically have own DNS records pointing to same/different IP; organize sections/services|
|Virtual Hosts (VHosts)|Configurations within web server allowing multiple websites/apps on single server; can be associated with TLDs or subdomains; each has own separate config|
|No DNS record?|Access via hosts file modification (map domain to IP manually, bypassing DNS)|
|VHost fuzzing|Technique to discover public and non-public subdomains/VHosts by testing hostnames against known IP|
|**Example — Apache VHost Config**||
|`<VirtualHost *:80>`|Name-based virtual host configuration|
|`ServerName www.example1.com`|Domain name for vhost|
|`DocumentRoot /var/www/example1`|Document root for content|
|Multiple vhosts|`www.example1.com`, `www.example2.org`, `www.another-example.net` hosted on same server|
|**Server VHost Lookup Process**||
|Browser Requests Website|Initiates HTTP request to web server associated with domain's IP|
|Host Header Reveals Domain|Browser includes domain name in request's Host header|
|Web Server Determines Virtual Host|Server examines Host header, consults vhost config for matching entry|
|Serving the Right Content|Server retrieves files from corresponding document root, sends as HTTP response|
|**Types of Virtual Hosting**||
|Name-Based|Relies solely on HTTP Host header; most common, cost-effective, easy setup; requires server support; limitations with SSL/TLS|
|IP-Based|Unique IP address per website; server determines by IP; no Host header reliance; better isolation; requires multiple IPs (expensive, less scalable)|
|Port-Based|Different websites on different ports (e.g., 80 vs 8080); used when IPs limited; less common/user-friendly; requires port in URL|
|**Virtual Host Discovery Tools**||
|`gobuster`|Multi-purpose; directory/file brute-forcing + vhost discovery; fast, multiple HTTP methods, custom wordlists|
|`Feroxbuster`|Rust-based; speed & flexibility; recursion, wildcard discovery, various filters|
|`ffuf`|Fast web fuzzer; vhost discovery by fuzzing Host header; customizable wordlist/filtering|
|**Gobuster — VHost Discovery**||
|`gobuster vhost -u http://<target_IP_address> -w <wordlist_file> --append-domain`|Brute force vhosts|
|`-u`|Target URL|
|`-w`|Wordlist file path|
|`--append-domain`|Appends base domain to each word (required in newer Gobuster versions)|
|`-t`|Increase threads for faster scanning|
|`-k`|Ignore SSL/TLS certificate errors|
|`-o`|Save output to file|
|**Example — Gobuster VHost Scan**||
|`gobuster vhost -u http://inlanefreight.htb:81 -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-110000.txt --append-domain`|Full vhost enumeration command|
|Output|`Found: forum.inlanefreight.htb:81 Status: 200 [Size: 100]`|
|**Caution**||
|Detection|VHost discovery generates significant traffic; may be detected by IDS/WAF; obtain proper authorization before scanning|

## Certificate Transparency Logs

|**Command / Option**|**Description**|
|---|---|
|**Core Concepts**||
|CT Logs|Public, append-only ledgers recording issuance of SSL/TLS certificates; global registry of certificates|
|Process|Every CA must submit new certificate to multiple CT logs; independent organizations maintain them; open for anyone to inspect|
|**Purposes**||
|Early Detection of Rogue Certificates|Monitoring CT logs → quickly identify suspicious/misissued certificates; swift revocation before malicious use|
|Accountability for CAs|CAs held accountable; violations publicly visible → sanctions or loss of trust|
|Strengthening Web PKI|Public oversight and verification of certificates enhances security/integrity|
|**CT Logs and Web Recon**||
|Advantage|Definitive record of certificates issued for domain + subdomains (unlike brute-forcing/wordlists)|
|Benefits|Historical and comprehensive view; includes inactive/hard-to-guess subdomains; may unveil subdomains associated with old/expired certificates (outdated software/configurations → vulnerable)|
|**Searching CT Logs — Tools**||
|`crt.sh`|User-friendly web interface; simple search by domain; displays certificate details, SAN entries; free, easy, no registration; limited filtering/analysis|
|`Censys`|Powerful search engine for internet-connected devices; advanced filtering by domain, IP, certificate attributes; extensive data, API access; requires registration (free tier)|
|**crt.sh — API Lookup**||
|`curl -s "https://crt.sh/?q=facebook.com&output=json" \| jq -r '.[] \| select(.name_value \| contains("dev")) \| .name_value' \| sort -u`|Automated search for 'dev' subdomains on facebook.com|
|`curl -s "https://crt.sh/?q=facebook.com&output=json"`|Fetch JSON output from crt.sh for matching domain|
|`jq -r '.[] \| select(.name_value \| contains("dev")) \| .name_value'`|Filter JSON results; select entries where `name_value` contains "dev"; `-r` = raw strings|
|`sort -u`|Sort alphabetically and remove duplicates|
|**Example Output**||
|Results|`*.dev.facebook.com`, `*.newdev.facebook.com`, `*.secure.dev.facebook.com`, `dev.facebook.com`, `devvm1958.ftw3.facebook.com`, `facebook-amex-dev.facebook.com`, `facebook-amex-sign-enc-dev.facebook.com`, `newdev.facebook.com`, `secure.dev.facebook.com`|

# Fingerprinting

|**Command / Option**|**Description**|
|---|---|
|**Core Concepts**||
|Fingerprinting|Extracting technical details about technologies powering a website/web app; digital signatures of web servers, OS, software components|
|**Why Fingerprinting Matters**||
|Targeted Attacks|Focus efforts on exploits/vulnerabilities known to affect identified systems|
|Identifying Misconfigurations|Expose misconfigured/outdated software, default settings, weaknesses|
|Prioritising Targets|Identify systems more likely vulnerable or holding valuable info|
|Building Comprehensive Profile|Combine with other recon findings for holistic view of infrastructure/security posture|

# Crawling

|**Command / Option**|**Description**|
|---|---|
|**Core Concepts**||
|Crawling (Spidering)|Automated process of systematically browsing the web; crawlers follow links from page to page collecting information|
|Crawlers|Bots using pre-defined algorithms to discover and index web pages (search engines, data analysis, web recon)|
|**How Web Crawlers Work**||
|Seed URL|Initial web page to crawl|
|Process|Fetch page → parse content → extract links → add to queue → crawl them → repeat iteratively|
|Scope|Can explore entire website or vast portion of the web (depending on config)|
|Example|Homepage → link1, link2, link3; visiting link1 reveals homepage, link2, link4, link5; crawler follows systematically|
|Key difference|Crawling discovers links by following them; fuzzing involves guessing potential links|
|**Crawling Strategies**||
|Breadth-First Crawling|Prioritizes width; crawls all links on seed page first, then links on those pages; useful for broad overview of structure/content|
|Depth-First Crawling|Prioritizes depth; follows single path as far as possible before backtracking; useful for finding specific content or reaching deep structures|
|**Extracting Valuable Information**||
|Links (Internal/External)|Map website structure, discover hidden pages, identify external relationships|
|Comments|Blogs/forums reveal sensitive details, internal processes, vulnerability hints|
|Metadata|Page titles, descriptions, keywords, author names, dates — context about content/purpose|
|Sensitive Files|Backup files (`.bak`, `.old`), config files (`web.config`, `settings.php`), log files (`error_log`, `access_log`); may contain passwords, API keys, database credentials, encryption keys, source code|
|**The Importance of Context**||
|Principle|Single piece of info may seem insignificant alone; combined with other findings → critical vulnerability indicator|
|Example — Links|Noticing URLs pointing to `/files/` → manually visit → directory browsing enabled → backup archives, internal documents, sensitive data|
|Example — Comments|Comment mentioning "file server" + discovered `/files/` directory → file server publicly accessible|
|Approach|Analyze data holistically; consider relationships between data points and implications for recon goals|

## robots.txt

|**Command / Option**|**Description**|
|---|---|
|**Core Concepts**||
|robots.txt|Simple text file in website root directory (e.g., `www.example.com/robots.txt`); follows Robots Exclusion Standard|
|Purpose|Virtual "etiquette guide" for bots; outlines which areas of website they can/cannot access|
|**How robots.txt Works**||
|Directives|Target specific user-agents (bot identifiers); tell bots which parts they can/cannot crawl|
|Example|`User-agent: *` / `Disallow: /private/`|
|Wildcard|`*` = all bots|
|Other directives|Allow access to specific directories/files; set crawl delays; provide sitemap links|
|**Structure**||
|Format|Plain text; each set of instructions ("record") separated by blank line|
|`User-agent:`|Specifies which crawler/bot rules apply to; `*` = all bots; specific (Googlebot, Bingbot)|
|**Common Directives**||
|`Disallow`|Specifies paths/patterns bot should not crawl (`Disallow: /admin/`)|
|`Allow`|Explicitly permits crawling specific paths even under broader Disallow (`Allow: /public/`)|
|`Crawl-delay`|Sets delay (seconds) between successive requests (`Crawl-delay: 10`)|
|`Sitemap`|Provides URL to XML sitemap (`Sitemap: https://www.example.com/sitemap.xml`)|
|**Why Respect robots.txt**||
|Not enforceable|Rogue bots could ignore it; most legitimate crawlers respect directives|
|Avoiding Overburdening Servers|Prevent excessive traffic that could slow/crash servers|
|Protecting Sensitive Information|Shield private/confidential info from search engine indexing|
|Legal and Ethical Compliance|Ignoring directives could violate terms of service or legal issues (copyrighted/private data)|
|**robots.txt in Web Reconnaissance**||
|Uncovering Hidden Directories|Disallowed paths often point to sensitive areas (backup files, admin panels, resources)|
|Mapping Website Structure|Analyze allowed/disallowed paths → rudimentary map; reveal unlinked sections|
|Detecting Crawler Traps|Some sites include "honeypot" directories to lure malicious bots; reveals security awareness/defenses|
|**Example Analysis**||
|`User-agent: *` / `Disallow: /admin/` / `Disallow: /private/` / `Allow: /public/`|All bots disallowed from `/admin/` and `/private/`; allowed `/public/`|
|`User-agent: Googlebot` / `Crawl-delay: 10`|Googlebot waits 10 seconds between requests|
|`Sitemap: https://www.example.com/sitemap.xml`|Sitemap provided for easier crawling/indexing|
|Inference|Website likely has admin panel at `/admin/` and private content in `/private/`|
